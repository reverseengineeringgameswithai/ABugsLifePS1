# Seed token collection and progression

## Confirmed retail behavior

Seed tokens are source-`0x3f` kinds `0x29..0x2d`. They advance the same five packed bytes used by plant-output selection; they are not a second inventory counter.

| Kind | Retail color family | Packed byte | Token handler | Store PC | Output object ID |
|---|---|---:|---:|---:|---:|
| `0x29` | brown/orange | `0x800A6598` | `0x800542F4` | `0x8005431C` | `0x16` |
| `0x2A` | blue | `0x800A6599` | `0x8005433C` | `0x80054364` | `0x17` |
| `0x2B` | green | `0x800A659A` | `0x800543B8` | `0x800543E0` | `0x19` |
| `0x2C` | purple | `0x800A659B` | `0x80054434` | `0x8005445C` | `0x18` |
| `0x2D` | yellow | `0x800A659C` | `0x800544D0` | `0x800544F8` | `0x2F` |

Each handler computes `n = (old + 1) & 7`, then stores `(n << 4) | n`. The high nibble is the currently selected output tier and the low nibble is the highest available tier. Collection therefore unlocks and immediately selects the new tier.

The modulo-8 wrap is not reachable in retail-authored progression. Level initialization begins at `[0x11,0,0,0,0]`; no level contains more than three brown tokens or more than four tokens of any non-brown color. The natural campaign domain remains `1 <= selected <= maximum <= 4` for unlocked colors.

## One-shot collection transaction

`source3f_dispatch` tests squared contact distance `< 2500`. For ordinary token kinds it calls `0x80057620`, writes `0x80000000` to the runtime source entry's Y field at `0x80053CD0`, and only then dispatches the color handler. The source entry consequently cannot retrigger until the authored source table is reconstructed.

Every color emits handler event `-3` through `0x80050994`. The common post-handler path also sends `-3` plus pickup coordinates through `0x8005044C`. These calls establish the feedback event and its location. They do not by themselves identify the exact audible sample, rendered primitive, or presentation frame.

## Non-brown registry and HUD

On the first unlock of blue, green, purple, or yellow, the handler appends lane index `1`, `2`, `3`, or `4` to the first zero nibble of `0x800B0196`. This is an ordered first-unlock registry, not a token total.

The HUD seed-meter loop renders lane 0 first. It then obtains each subsequent lane index from the next low nibble of `0x800B0196`, reads `0x800A6598 + lane`, and uses that packed byte's high nibble as the displayed tier. Gameplay initialization clears the registry.

## Lifecycle boundaries

Level loading clears 168 bytes from `0x800A6500`, then writes brown `0x11`. Ordinary respawn does not rewrite the packed lanes. The memory-card serializer/deserializer copies the separate 19-byte unlock array at `0x8009B878`; it has no reference to `0x800A6598..0x800A659C`. Seed-output tier progress is therefore per-level runtime state, not memory-card progression.

Reloading a level reconstructs authored source-`0x3f` entries and makes its tokens available again. Within the current loaded source table, the retirement sentinel makes a collected token one-shot.

## Correction to the latent helper interpretation

`0x80053754` contains generic `((old + 1) & 7) * 17`, reskin, and first-unlock registry logic, but pristine resident code has zero direct jump/call references and zero literal-pointer references to it. It is an unowned generic upgrade helper. It is not the active X-button output-cycle path; that path changes only the selected high nibble and is documented in [[Seed_plant_output_binding]].

# Retail Gameplay Completeness Gap Audit

> [!warning] Audit note, not Canon
> This is a broad completeness audit and may summarize older findings. For current canonical Gold Berry/drop/permanence/HUD facts use [[SYS_contact_objects_and_drops]], [[SYS_enemy_death_and_permanence]], [[SYS_hud_counters]], and [[MOD_gold_berry_token_drop]]. Resolved wrong hypotheses live under `Archive/Wrong Hypotheses/`.

> Player-facing audit of what is still missing before this RE/editor work can make **A Bug's Life (PS1)** look and behave like the retail game, not merely boot a modified LEVEL01. This complements [[Gap Audit]] and [[LEVEL01 Level-Edit Punchlist]]: those track engineering gaps; this note tracks the **retail completeness target** across mechanics, objects, level design, power-ups, enemies, and visual presentation.

## Scope and yardstick

**Yardstick:** a viewer/player should recognize the result as the PS1 game: the same collectathon loops, seed/plant power-up chain, berries, enemies, level-exit goals, bosses, HUD, camera, textured terrain, props, characters, music/SFX, and per-level staging.

**External gameplay baseline:** public gameplay summaries describe the game as a 3D platformer split into **five lands of three levels each**. Level completion is by exit, objective, or boss. Core mechanics include berry throwing, stronger / homing / gold berries, plantable seeds that change function via seed tokens, grain collection, FLIK letters for extra life, telescopes, health leaves, and a grain harvester in some levels. Reference: https://en.wikipedia.org/wiki/A_Bug%27s_Life_%28video_game%29

**Local evidence baseline:** current repo/vault work is strongest for **LEVEL01** editing, native type-0x3f collectibles, floor/collision edits, seed placement, berry projectile mechanics, enemy AI shape, spawn/warp structure, and partial visual-fidelity in the editor. Disc files confirm multiple stage/resource directories (`REBUILD/files/LEVEL00` through `LEVEL10`) and many per-level sidecars, so retail breadth is larger than the editor's present LEVEL01-first coverage.

## Re-audit result (2026-07-01)

This pass re-checked the note against the current vault/code, not just the original completeness framing. Several items are **more complete than the first version said**:

- **LEVEL01 exit / goal trigger:** now solved to the disc source and GUI layer: chunk-32 sector region code `+0x2c`, sector 177 in retail LEVEL01; relocation to another sector is in-game proven and editor-wired. Retail-wide exit/goal mapping remains open.
- **Camera follow law:** the normal gameplay follow camera is decoded and validated; remaining camera gaps are byte-exact viewport/pixel mapping, boom collision/LOS pull-in, non-normal camera modes, telescope/cutscene/boss modes.
- **Telescope / hint device:** kind `0x30` is no longer just "unknown telescope placement"; it has bobbing/render behavior, hint/checkpoint contact behavior, and relocation proof. Remaining gap is all-level semantics and kind `0x31`.
- **Health/lives HUD:** health leaf (`0x800a7e2a`) and lives (`0x800a65a0`) are mapped; health-leaf pickup/drop behavior is still not cataloged.
- **Menu/save/FMVs/audio:** menu navigation and memory-card save/load overlay paths are statically decoded; FMV manifest/trigger and LEVEL01 XA music mapping/replacement are proven. Remaining gaps are menu rendering/options body fields, positive SFX key-on trace, SFX event map, and MDEC call site inside `FMV.BIN`.
- **Authoring pipeline:** Blender import/export/object edits, terrain-height export, coarse collision matching, and a gentle terrain boot-test are done for LEVEL01. Remaining gap is retail breadth and exact in-editor presentation.
- **Level-format generality:** DAT/RAW formats generalize across all 10 level directories and runtime engine structures are confirmed fixed across several stages. Remaining gap is per-level content/role mapping, not parser/codec generality.

Net: this note should be read as a **retail-completeness gap list**, not as a list of missing low-level primitives. Several primitives are done; the missing work is now mostly **campaign-wide inventories, presentation integration, boss/special-case overlays, and per-level objective mapping**.

## Custom-level end-goal status

**Goal:** make entirely new levels while reusing the game's existing textures where practical.

**Best-fit route:** use the [[Tier 3 - Custom Level Engine]] / [[Tier 3 - Level Replacement Phases]] path, not the native-format LEVEL01 editor path as the final architecture. The native editor path is valuable for understanding retail data and borrowing assets, but arbitrary new level design should not depend on fully decoding every original terrain/layout format.

**Already solved enough to proceed with Tier 3 prototypes**
- Custom collision/rendering/spawn has already produced a cold-boot playable custom level.
- Blender-authored geometry is already part of the pipeline.
- Native texture reuse is the viable texture strategy: use the existing VRAM tile set / texpage / CLUT palette and authored Blender UVs. Uploading broad new texture sets is currently a poor default because native VRAM is already crowded.
- Deleting or bypassing native terrain/objects is the right design direction for blank-slate levels; render-side suppression alone has known limits, so source-side removal or replacement is preferred.

**More RE is still required, but it is targeted**
- Build a usable texture/material atlas from the existing game pages so new Blender levels can intentionally choose retail textures instead of guessing by raw texpage/CLUT values.
- Finish the object strategy: decide which native actors are kept as-is, which are replaced by custom markers, and which source records should be removed so old layouts do not leak into new levels.
- Bind gameplay objects needed for new stages: exits, pickups, enemies, seed/plant outputs, health leaves, swinging/vine actors, grain harvester, and boss/special mechanics if those will be used.
- Establish scale/performance budgets for larger custom levels: triangle count, wall/collision count, draw ordering, culling, and memory layout.
- Polish visual integration: render ordering, occlusion, transparency, actor/model placement, and any residual native scenery or floor fragments.

**Recommendation:** do not spend the next phase trying to make the entire native level-layout system author arbitrary new worlds. Use native RE to harvest textures, actor behavior, HUD/state, and known mechanics; use Tier 3 as the level authoring substrate.

## Executive Summary

The project can already edit large parts of LEVEL01 and several native mechanics. It does **not yet have retail-complete visual/gameplay coverage**. The largest remaining gaps are:

1. **All-level breadth foundation is now covered:** `RCG-001` has a campaign matrix for all 15 stages and all `LEVEL00..LEVEL10` resource directories; remaining breadth work is semantic (objectives/exits/overlays/material profiles), not missing inventory.
2. **Visual identity:** real-time emulator-backed view and Blender authoring exist, but offline/editor views still lack retail-grade pickup/FX rendering, transparency, exact material/CLUT detail, and all-level visual themes.
3. **Character, plant, and object presentation:** `.ALL` / `.ANM` are byte-exact and the actor/model binding catalog now covers Flik, enemies, bosses, plant outputs, pickups, seeds, harvester variant, and animated props; remaining work is offline renderer import/polish, not identity discovery.
4. **Seed/plant gameplay chain:** seed placement and the token-colour -> plant-output -> plant behavior matrix are documented; residuals are purple berry grant ids, per-level plant manifests, handler fine detail, and per-level use census.
5. **Level goals and level design:** LEVEL01 exit sector is solved and relocatable; `RCG-003` now has a save-state-backed sector-trigger matrix plus live route proof for the simple "be here" endings (`LEVEL02`, `LEVEL04`, `LEVEL05`, `LEVEL14`). Conditional character/collection/rescue endings and boss levels stay separate.
6. **Bosses and special encounters:** regular enemy AI is well modeled; Thumper/Hopper/Thud combat bookkeeping and some boss overlays remain partial.
7. **Audio/FMVs/front-end polish:** assets are extractable and some music replacement is proven, but in-engine runtime playback/menu/save/front-end behavior is not fully mapped.

## Gameplay System Coverage

### Collectibles and Power-ups

**Strong / proven**
- Grain move/add/delete, dynamic HUD total, and all-grain emblem behavior are proven in LEVEL01. See [[LEVEL01 Level-Edit Punchlist]] §6 and [[Grain emblem and HUD total mod]].
- FLIK letter placement and 4-letter glyph replacement are proven; the word is texture art, not text. See [[LEVEL01 Level-Edit Punchlist]] §7 and [[HUD letter glyphs and word swap]].

- Telescopes: kind `0x30` bob/hint/checkpoint behavior and relocation are decoded; all-level placement semantics and any distinct telescope camera/rotating-view mode still need confirmation.
- Grain harvester: model exists; mechanic, equip trigger, enemy/grain attraction effects, and affected levels are not documented.
- Full seed/plant matrix: token colors, plant outputs, model names, behavior, and per-level use cases.
- Swinging/vine traversal: not yet documented as a distinct mechanic; needs source actor/plant, input/contact rules, camera interaction, and per-level use.
- Kind `0x31`: has a dedicated animated construct / checkpoint-like source path, but its retail use is unresolved.

## Visual / Audio Completeness

### Visual "looks like PS1 ABL"

**Done or close**
- Real game view via isolated DuckStation is the most faithful path.
- **Editor visual-fidelity architecture is closed:** [[Editor Visual Fidelity Baseline]] makes the live DuckStation view the 1:1 verifier and explicitly bounds offline Blender/GL to authoring previews/harnesses.
- Offline LEVEL01 floor and many props can now be shown with decoded geometry/textures.
- `.ALL` / `.ANM` formats are decoded enough for inspection and future renderer work.
- Blender can import LEVEL01, export object edits, export terrain heights, match coarse collision, and build discs for gentle walkable terrain.
- The flat sky is understood: it is a GP0 `0x02` background fill, not a bitmap, sourced from the sky/DRAWENV color cache and rebuilt every frame.
- Tier-3 understands the background-vs-scene ordering enough to preserve the sky/backdrop pass while walking: the DrawOTag hook sees a populated background OT chain first, then the scene chain with terrain/Flik/objects/HUD.

#### Sky / backdrop status

**Solved / usable**
- Static sky color: confirmed as a per-frame GP0 fill (`0x02BBGGRR`), not a backdrop image. RAM recolor lever is the sky DRAWENV cache; persistent source is LEVEL.RAW-derived but one note has an unresolved byte-offset discrepancy, so authoring should treat the RAM/cache path as confirmed and the exact on-disc table offset as needing re-check before permanent edits.
- Runtime pass split: background chain vs scene chain is confirmed at the DrawOTag DMA kick. This is enough for Tier-3 to avoid drawing custom geometry in front of the entire native presentation by mistake and to preserve the native sky/backdrop pass.
- Walking/camera behavior at the pass level: the background pass remains separate while the scene pass updates with camera-projected terrain, Flik, objects, and HUD/overlay content.

**Still a gap**
- The richer player-facing backdrop is not fully decoded as an authorable asset. The far grass/dirt horizon band and backdrop-like wall strips are currently described as native env/sprites or kept backdrop/sprite layers, but their exact source records, image-vs-mesh breakdown, and camera/parallax rules are not cataloged.
- New custom levels can keep the native backdrop pass, but replacing it cleanly or making per-level custom backdrops still needs targeted RE.

**Still visibly wrong / incomplete**
- Pickups often render as proxies instead of retail sprites/models.
- Flik/enemies/plants are absent or not animated in the offline editor.
- Transparency, CLUT/material exactness, face culling, and camera matching remain visible defects.
- Walls/master terrain layer is not permanently editable and not fully decoded.
- Sky/background is partly understood: the flat sky is a per-frame GP0 `0x02` fill and Tier-3 preserves the background OT pass, but the far horizon/backdrop layer is not yet an authorable, fully decoded asset with documented camera/parallax rules.
- Blender currently uses placeholder colours rather than baked retail materials/textures.
